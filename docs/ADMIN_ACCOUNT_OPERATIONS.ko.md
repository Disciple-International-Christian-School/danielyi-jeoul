# 개인 관리자 계정 운영

**Language / 언어:** [English](ADMIN_ACCOUNT_OPERATIONS.md) | [한국어](ADMIN_ACCOUNT_OPERATIONS.ko.md)

공유 역할 계정에서 개인 인증 계정으로 전환하면서 업무 연속성과 감사 추적을 보존한다.

## 1. 개인계정의 이유

공유계정은 어느 역할이 작업했는지만 설명한다. 개인계정은 인증된 작업자를 식별한다. 신규 기록의 작성·수정자 UUID와 추가 전용 감사로그가 개인 책임성을 뒷받침한다. 학생의 앱 이용 방식은 바뀌지 않는다.

## 2. 전환 순서

공유계정을 먼저 삭제하지 않는다. 개인계정 생성 → 실제 업무 시험 → 담당범위 확인 → 감사로그 검토 → 공유계정 사용 중단 → 비활성화 순서로 진행한다. 비활성화 후에도 과거 기록은 유효하다.

## 3. 계정 생성

활성 SEONDO 선도부장만 관리자 계정 화면을 연다. 로그인 ID·표시 이름·역할·담당범위·해당 시 부장 여부를 지정한다. ID는 3–32자이며 소문자·숫자·점·밑줄·하이픈만 허용한다. 내부 인증 이메일은 <login_id>@scale.dics.kr로 생성되지만 로그인 화면에는 ID만 입력한다.

## 4. 임시 비밀번호

서버 함수가 강한 난수 비밀번호를 생성한다. 부장에게 한 번만 반환하며 Git·admins 테이블에 저장하지 않고 다시 표시하지 않는다. 당사자에게 적절한 비공개 경로로 전달한다. 이슈·PR·공유 문서·공개 채팅에 쓰지 않는다.

## 5. 첫 로그인

신규계정은 must_change_password=true로 시작하며 일반 운영 화면 대신 비밀번호 변경 화면만 표시한다. 12자 이상, 대문자·소문자·숫자·특수문자가 필요하다. JWT가 필요한 change-admin-password Edge Function이 실제 Supabase Auth 변경에 성공한 뒤에만 완료 플래그를 내린다.

## 6. 담당범위

SEONDO: ELEMENTARY=G1–6, MIDDLE=G7–9, HIGH=G10–12, ALL=선도부장. 부장은 SEONDO/ALL로 정규화한다. SASAENG는 생활지도 담당범위와 선도부장 지위를 갖지 않는다.

## 7. 비활성화

프로필 삭제 대신 비활성화한다. private.current_admin_role()이 운영 역할을 반환하지 않고 보호 화면 접근이 막히지만 created_by/updated_by와 감사 이력은 남는다. 이후 검토·재활성화할 수 있다. 마지막 활성 선도부장은 제거할 수 없다.

## 8. 작성 당시 전환 상태

프로필 2, 활성 관리자 2, 활성 부장 1, 신규 개인계정 0, 비밀번호 변경 필요 계정 0. 따라서 공유계정이 운영 대체 경로로 남아 있었다. 현재 상태는 운영 확인이 필요하다.

## 9. 배포 구성

DB: admins.login_id / must_change_password / last_password_changed_at / provisioned_by, v_admin_accounts, register_admin_profile(...), update_admin_profile(...).

서버 함수: provision-admin-account, change-admin-password. 모두 유효한 JWT가 필요하다. Auth Admin API와 서비스 인증정보는 서버에만 존재하며 브라우저 JavaScript에 노출하지 않는다.

## 10. 최초 보급 점검

1. 부장이 계정을 생성한다.
2. ID·임시 비밀번호를 비공개로 전달한다.
3. 담당자가 로그인하고 새 비밀번호를 설정한다.
4. 표시 역할·담당범위를 확인한다.
5. 통제된 업무나 비파괴 시험을 수행한다.
6. 감사 주체 이름과 범위 밖 접근 차단을 확인한다.
7. 정상 사용을 계속한다.

공유계정 중단 전에 순차적으로 수행한다.

## 11. 공유계정 종료 조건

모든 필수 작업자의 개인계정·첫 변경·정확한 범위, 부장 접근의 대체 가능성, 개인 감사 주체, 공유 인증정보 없는 일상 업무가 확인되어야 한다. 일상 화면에서 숨기기 위해 과거 Auth/프로필을 삭제하지 않는다.

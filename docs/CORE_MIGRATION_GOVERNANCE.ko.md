# DICS Core 마이그레이션 관리

**Language / 언어:** [English](CORE_MIGRATION_GOVERNANCE.md) | [한국어](CORE_MIGRATION_GOVERNANCE.ko.md)

여러 학교 앱이 공유하는 Supabase DB의 임시 관리 규칙이다. core·discipline·study_planner·computer_lab 및 향후 assessment가 같은 프로젝트를 사용한다. 병렬 작업에서 운영 DB가 Git보다 먼저 바뀐 사례가 있어 책임자와 인수인계 규약이 필요해졌다.

## 1. 임시 기준 저장소

별도 DICS-Core 저장소가 생기기 전 학교 조직의 danielyi-jeoul 저장소에 있는 supabase/migrations/와 supabase/migration-ledger.json을 중앙 원장으로 사용한다. 과거 shualoalumin 경로는 이전 소유자 표기다. Daniel은 생활지도 앱이며 이것이 최종 소유 구조는 아니다.

## 2. 장기 목표

DICS-Core는 공통 스키마, 학생·학기·학급·학적, 신원·외부 연결, 공통 역할, 도메인 간 실행 순서, 검증 스크립트, 재해복구·재구축 절차를 소유한다. 앱별 저장소는 프론트엔드·업무 로직·안전하게 분리되는 도메인 이관을 소유한다.

## 3. 도메인별 책임

Core는 core.*, Daniel은 discipline.*, SP는 study_planner.*, 컴퓨터실은 computer_lab.*, 평가 앱은 assessment.*를 담당한다. 도메인 간 변경은 중앙 원장에서 조정한다.

## 4. 운영 구조 변경 완료 조건

Git에 마이그레이션이 있고, 파일명이 실제 운영 버전·이름과 같으며, 원장 TRACKED 항목이 존재하고, 멱등성 또는 일회성 순서가 명확하고, 새 환경에서 재현 가능하며, 문서·이력이 갱신되어야 한다. 다른 세션이 운영을 먼저 바꾸었다면 구조를 대조해 조정 이관을 기록한다.

## 5. 구조와 데이터

테이블·뷰·RPC·트리거·RLS·인덱스·개인정보 없는 상수는 Git에 둔다. 실명·학번·PIN·생년월일·명부·검증된 신원 연결표는 두지 않는다. 운영 데이터 변경의 방법과 집계 결과만 기록한다. 운영 이관 이력에 데이터 변경이 있다면 민감 SQL 대신 LIVE_ONLY_DATA 항목을 남긴다.

## 6. 이름과 수정 이력

타임스탬프 파일을 사용한다. 이미 적용된 SQL을 소급 덮어써 오류를 숨기지 않고 원본 뒤에 수정 이관을 추가한다.

## 6A. 운영 원장 규약

TRACKED는 구조 SQL이다. 원장 version+name이 정확한 Git 파일명과 일치해야 한다. 파일 누락·이름 불일치·원장 없는 SQL·중복 버전은 CI 실패다.

LIVE_ONLY_DATA는 비공개 명부, 명부 수정, 환경별 인증 연결, 구조 재현과 무관한 과거 seed 등이다. 버전·사유는 기록하되 SQL을 Git에 두지 않는다. 이름 자체가 민감하면 가린다. 해당 버전 SQL이 있으면 CI가 실패한다.

과거 점검: 운영 55, 구조 51, 데이터 전용 4, 추가 Git 파일 0. 현재 수치는 원장으로 확인한다.

## 6B. 새 이관 적용 후

실제 운영 버전 조회 → Git 파일 대조 → 필요 시 운영 버전으로 파일명 정렬 → 원장 갱신 → npm run check:migration-ledger → CI 통과 → 중요한 구조 판단을 개발 일지에 기록한다. 실행 전에 정한 시각과 운영이 기록한 시각이 같다고 가정하지 않는다.

## 7. 병렬 AI 인수인계

저장소·브랜치·커밋·운영 이관 이름·변경 스키마/테이블·검증 결과·롤백/수정 전략·다음 의존성을 남긴다. SP에서는 이슈 #2를 조정에 사용했다. 향후 Core에도 중앙 조정 이슈가 필요하다.

## 8. 인증 이름공간

정규 학생 신원, Core 내부 로그인, 외부 로그인을 구분한다. 각각 core.students.id, core.students.auth_user_id, core.external_auth_identities로 표현한다. UUID 형식이 같다고 같은 인증 주체가 아니다.

## 9. 새 환경 검증

문서화되지 않은 운영 변경에 의존하지 않고 Git에서 DB 구조를 재구축할 수 있어야 관리가 완료된 것이다.

## 10. 프로젝트 기록의 의미

처음부터 기업식 관리가 있었던 것이 아니다. 여러 학교 앱의 공통 신원과 AI 병렬 작업이 실제 복잡성을 만들면서 이관 관리가 발전했다. 이 과정 자체가 근거가 있는 개발 기록이다.

# Supabase 공통 DB 용량 — 과거 논의

**Language / 언어:** [English](SUPABASE_CAPACITY.md) | [한국어](SUPABASE_CAPACITY.ko.md)

> 기존 HTML의 한국어 스크린샷 20개를 읽기용으로 정리한 판이다. 원본은 대화 중간에서 시작·종료되며 완전한 대화록이 아니다. 현재 요금·한도·승인된 운영 계획으로 해석하지 않는다. 원본 HTML/PDF는 보관 자료로 남긴다.

## 질문

하나의 Supabase 프로젝트를 스키마·테이블로 나누면 프로젝트 수 때문에 유료로 바꿀 필요가 없는가? 당시 논의는 여러 학교 앱이 하나의 DB를 공유할 수 있으므로 앱 수와 DB 프로젝트 수를 구분해야 한다고 답했다.

## 제안 구조

공통 학생·계정/인증·학적은 Core에 두고 학습·생활지도·컴퓨터실·배치고사·SAT/TOEFL·향후 포털/현황판을 스키마로 나눈다. 두 번째 개발 프로젝트는 실제 학생 자료 없이 시제품·이관·구조 시험에 사용하고, 실험 MVP·개인 학습은 별도 무료 조직/프로젝트도 검토했다.

초기 예시는 public 학생/반/학적, discipline 사건/보상/주간·월간 요약, study_planner 과제/진척/배정, computer_lab 출입/세션/기기 로그, testing 영어/수학/말하기 기록이었다. 현재 SQL 계약이 아닌 개념도다. 특히 초기 student_auth_pins 같은 표현은 현재 설계로 대체됐다. 인증정보는 Auth에서 관리하며 학생 프로필에 평문 PIN을 저장하지 않는다.

## 유료 운영을 검토한 이유

앱 개수보다 휴면 중지·백업/복구·컴퓨팅·사용량·안정성을 강조했다. 방학 동안 사용량이 줄면 개학 시 DB를 재개해야 하는 불편이 생길 수 있다. 별도 프로젝트마다 자원이 있어 분할은 관리·컴퓨팅 비용도 늘릴 수 있다.

MVP/내부 시험은 무료 단일 프로젝트로 시작할 수 있고 실제 일상 업무에서는 연속성과 복구를 기준으로 유료를 평가하자는 의견이었다. 구매 결정이나 용량 시험 결과가 아니다.

## 원본의 과거 수치

| 항목 | 당시 대화의 주장 |
| --- | --- |
| 무료 활성 프로젝트 | 2개 |
| 낮은 사용량 | 7일 후 중지 가능 |
| DB | 500MB |
| 월 활성 사용자 | 50,000 |
| 저장소 | 1GB |
| 전송 | 비캐시 5GB + 캐시 5GB |
| Edge Function | 500,000회 |
| Realtime 메시지 | 200만 |
| 무료 단일 파일 | 50MB |

번역 충실도를 위해 보존한 값이며 구매·배포 전 공식 조건과 계정 상태를 다시 확인한다. 벌점/컴퓨터실 각 수만 행·학습 과제 수십만 행도 충분할 수 있다는 말은 추정이다. 실제 크기·인덱스·보존기간·조회 패턴 측정은 없었다.

## 파일과 복구

텍스트·숫자·시간보다 이미지·PDF·음성이 저장/전송량을 크게 만들 수 있다. 말하기 녹음은 외부 객체 저장소나 분리된 미디어 업무로 관리하는 안을 논의했다. 요금제별 관리형 백업 차이와 학생·학습·평가 자료의 복구 전략 필요성을 강조하던 중 마지막 화면이 끝난다. 누락된 결론을 임의로 추가하지 않는다.

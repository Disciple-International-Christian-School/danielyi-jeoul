# Study Planner → DICS Core 이관 실행서

**Language / 언어:** [English](SP_CORE_MIGRATION_RUNBOOK.md) | [한국어](SP_CORE_MIGRATION_RUNBOOK.ko.md)

> 기록상 상태: 준비. 기존 SP 서비스를 유지하면서 학습 도메인 데이터를 Core로 옮기며 학생 원본을 중복 생성하지 않는다.

## 1. 출발지와 목적지

기존 SP ref=wqvtgrcwiumglohbybih, Core ref=jgrzsfomcwfiukkaqtos. 정규 학생은 core.students.id, 사람용 번호는 student_no, Core 내부 선택 로그인은 auth_user_id, 외부 계정은 core.external_auth_identities다. 목적 도메인은 study_planner.*다.

## 2. 필수 규칙

일반 테이블에 PIN을 복사하지 않고 실제 연결표를 Git에 넣지 않는다. 이름만으로 일치 확정하지 않는다. 목적지 검증 전에 SP를 중지하지 않는다. 가능한 원본 도메인 UUID를 보존하고 Auth와 학생 신원을 분리한다. 학기는 Core 원본을 재사용하며 모든 단계 전후에 행 수를 비교한다.

## 3. A — 원본 재고

학생·교사·학기·주차·시간블록·입력기간·과목태그·학기목표·주간계획/목표·계획항목·항목/블록실행·과제양식·교사댓글 건수를 조회한다. 스키마와 Git의 차이, 활성/비활성, 시험계정, 고아 FK, 인증 연결 수를 확인한다. Git·이슈에는 집계만 기록한다.

## 4. B — 신원 연결

학생 UUID·학번·이름·학년·반을 신뢰 경로에서 대조한다. 비학생 번호 명시 제외 → 검증된 학교 식별자로 대조 → 이름/학년/반은 보조 증거 → 모호 항목 수동 검토 → SP 연결 컬럼 기록 → 학번 유일성 확인 → 외부 Auth 연결표 기록 → Core에서 계정이 만들어진 뒤에만 내부 auth_user_id 반영 순이다.

기대 실학생 수와 연결 수가 같고 학번·외부 신원·Core 내부 Auth 중복이 0이어야 한다. 데이터 이관 전에 모호 항목도 0이어야 한다.

## 5. C — 기준 데이터

시간블록·입력기간·과목태그를 코드/UUID 보존 방식으로 이관하고 정확한 행 수·유일키를 확인한다.

## 6. D — 학사 시간

SP 학기를 Core academic_terms에 명시적으로 연결한다. 당시 현재 학기는 2026-FALL, 2026-08-19~2027-01-21이었다. 주차는 Core 학기 UUID를 참조한다. 같은 의미의 학기를 도메인에 중복 생성하지 않는다.

## 7. E — 학생 업무 데이터

학기목표 → 주간계획 → 주간목표/계획항목 → 항목/블록실행 → 교사댓글 순으로 복사한다. 과제양식은 과목태그·학생 연결 후 복사할 수 있다. 학생 FK는 SP 외부 Auth → 검증된 연결 → Core UUID → 도메인 FK로 변환한다.

## 8. F — 검증

테이블별 원본·목적지 건수, 누락 FK, 중복 유일키를 확인한다. 실제 표본에서 학기목표 조회, 주간 상태, 날짜·시간블록, 실행 상태/분량/from-card/window, 교사 연결을 확인한다. RLS 적용 후 다른 학생 자료를 읽지 못해야 한다.

## 9. G — API/RLS 전환

외부 SP UUID를 Core auth.uid()로 취급하지 않는다. Core 로그인 계정 생성/이관 → Core-local auth_user_id 기준 RLS → 필요한 뷰/RPC → 검증용 프론트엔드 → 병행 업무 비교 → 검증 후 운영 전환 순이다.

## 10. H — 기존 서비스 종료 판단

운영 원본 → 읽기 전용 대체 경로 → 보관 백업 → 종료 결정 순으로 진행한다. 목적지 데이터·인증 완료, 설명 안 되는 수 차이 없음, 최소 한 정상 운영 주기 검증이 필요하다. 이전 프로젝트를 즉시 삭제하지 않는다.

## 11. 보고서 근거

단계별 일시·원본/목적지 건수·발견 예외·판단·이관/커밋 참조·CI·운영 검증·롤백 방법을 남긴다. 기억에 의존해 성과를 재구성하지 않는다.

> **ACTIVE DESIGN DOCUMENT · 2026-09-25**

## 1. 이번 개선의 핵심 방향

다니엘의 저울을 단순한 상·벌점 CRUD에서 다음 흐름을 지원하는 운영 콘솔로 확장한다.

```text
아침 벌점 취합
  ↓
빠른 일괄 입력
  ↓
당일 반성문 대상 자동 생성
  ↓
담당 선도부가 학년군별 취합
  ↓
반별 공지/출력
  ↓
주말 주간 정산
  ↓
체력훈련 대상 확인/출력
  ↓
관리자 종료형 정산기간 누적
  ↓
징계위원회 대상 확인
```

장기적으로는 Study Planner 등 다른 DICS 시스템과 학생 신원을 공유할 수 있도록 데이터 모델을 준비한다.

## 2. 학교 공통 학생 식별자 방향

### 현재

- 다니엘의 저울: 자체 `students.id`(serial), 이름/학년 중심
- Study Planner: Supabase Auth user UUID + `student_no`
- SP 일부 학생: 학번 + 6자리 PIN으로 로그인

### 원칙

앞으로 앱 간 학생을 연결할 때 **이름을 키로 사용하지 않는다.**

```text
school student
    ↓
student_no  ← 학교 공통 식별 키
    ├─ Daniel's Scale
    ├─ Study Planner
    └─ future DICS apps
```

다니엘의 저울 `students`에도 `student_no`를 추가한다.

### PIN

PIN은 학생 프로필 데이터가 아니라 **인증 수단**이다.

- PIN 평문을 일반 학생 테이블에 저장하지 않는다.
- Git에 넣지 않는다.
- 인증 프로젝트의 Auth password로만 관리한다.
- PIN 배포가 필요하면 최초 발급용 별도 운영 문서를 사용하고 이후 폐기/보호한다.

### 장기 방향

당장은 두 Supabase 프로젝트를 강제로 합치지 않는다.

대신 모든 시스템에서 동일한 `student_no`를 사용해 나중에 학교 공통 Directory/Auth 계층으로 이동할 수 있게 한다.

> **중요:** 성별과 생년월일은 원본 명부에는 있지만, 생활지도 사이트 기능에 꼭 필요한 정보가 아니다.  
> 데이터 최소화 원칙에 따라 현재 다니엘의 저울 DB에는 자동으로 복제하지 않는다. 추후 학교 공통 학생 Directory를 만들 때 별도로 검토한다.

## 3. 학생 학적 / 반

다니엘의 저울 학생 기본 정보는 운영상 다음 수준까지 필요하다.

```text
student_no
name
grade (1–12)
homeroom
active/deleted status
```

특히 G9은 A/B 분반이 있으므로 단순 `grade=9`만으로는 반별 공지를 만들 수 없다.

예:

```text
grade = 9
homeroom = "9-A"
```

반 배정 실제 행 데이터는 Supabase에만 적재한다.

---

## 4. 점수 계산 원칙

원본 상점과 벌점은 계속 별도 보존한다.

```text
positive_points = 상점
negative_points = 벌점

net_penalty = negative_points - positive_points
```

즉 **원본 데이터를 상쇄해서 지우는 것이 아니라**, 처분 판정 시 계산된 NET 값을 추가로 사용한다.

## 5. 주간 정산

주간 기준:

- 월요일 시작
- 매주 새로 계산
- 벌점 사유 발생 횟수 **3회 이상**, 또는
- 주간 `net_penalty >= 8`

이면:

```text
체력훈련 대상
```

주간 출력 화면에서 최소 다음을 보여준다.

| 항목 | 내용 |
|---|---|
| 학생 | 이름 / 학년 / 반 |
| 벌점 발생 횟수 | 주간 NEGATIVE record 수 |
| 상점 | 주간 상점 |
| 벌점 | 주간 벌점 |
| NET | 벌점 - 상점 |
| 판정 | 체력훈련 대상 여부 |

주말에 담당자가 이 화면을 보고 출력할 수 있어야 한다.

---

## 6. “월간” 정산은 달력 월이 아니다

기존 구현의 calendar month 방식은 실제 DICS 운영과 맞지 않는다.

실제 기준은 **귀가 사이클 단위의 관리자 종료형 정산기간**이다.

예:

```text
정산기간 #1
09/07 시작
  ↓
계속 누적
  ↓
09/27 귀가
  ↓
관리자가 [정산 종료] 클릭

정산기간 #2
09/28 시작
...
```

귀가 일정이 불규칙하면 관리자가 종료하지 않는다.

따라서:

> 버튼을 누르지 않는 것 자체가 “다음 주까지 누적”이라는 운영 선택이다.

DB에는 `settlement_periods`를 두고 동시에 하나의 OPEN period만 존재하도록 한다.

---

## 7. 징계위원회 대상

현재 열린 정산기간에서 다음 중 하나이면 대상이다.

- 체력훈련 판정 주차가 **3회 이상**
- 정산기간 `net_penalty >= 20`

```text
physical_training_weeks >= 3
            OR
settlement_net_penalty >= 20
            ↓
징계위원회 회부 대상
```

체력훈련 “3회”는 임시 숫자를 별도 입력하기보다, 각 주차의 체력훈련 대상 판정을 원점수에서 다시 계산할 수 있게 하는 것을 우선한다.

---

## 8. 부서활동 가산점 자동 입력

`부서활동_가산점.xlsx`의 실제 명단은 Git에 넣지 않는다.

목표 흐름:

```text
활동 배정
  ↓
학생별 주간 상점 rule
  ↓
매주 월요일 자동 생성
  ↓
point_records (POSITIVE)
```

필수 조건:

1. 같은 학생/같은 주차에 중복 생성 금지
2. 자동 생성 기록임을 식별 가능
3. 활동 중단/변경 날짜 관리
4. 관리자가 자동 생성 결과 확인 가능
5. 잘못 생성된 행도 hard delete하지 않고 추적 가능

정확한 점수와 활동 목록은 선도부 협의 후 확정한다.

## 9. 반성문 운영

### 기본 마감

#### G7–G12

벌점 발생 당일:

```text
기본 마감 = 17:00
```

오후 벌점 등 특별 사유가 있으면 선도부 재량으로:

```text
연장 마감 = 21:00
```

### G1–G6

당일 저녁 제출을 요구하지 않고:

```text
다음 등교일 아침 제출
```

을 기본 원칙으로 한다.

따라서 기존 `submission_deadline date`만으로는 부족하며, 정확한 시간까지 표현하는 `due_at timestamptz`가 필요하다.

---

## 10. 반성문 담당 구조

선도부 구성원은 개인 계정을 사용하고 담당 범위를 가진다.

권장 범위:

```text
ELEMENTARY → G1–G6
MIDDLE     → G7–G9
HIGH       → G10–G12
LEAD       → 전체 / 주간 정산 / 보고
```

실제 담당자 이름은 공개 Git 문서에 기록하지 않고 Supabase 운영 데이터로만 둔다.

선도부장은:

- 누락 확인
- 통합 입력
- 주간 정산
- 담당교사 보고

흐름을 볼 수 있어야 한다.

## 11. 아침 벌점 입력 UX

현재 종이 벌점 시트를 오전에 일괄 입력하는 현실을 기준으로 UX를 최적화한다.

### P1

**빠른 일괄 수동 입력**

- 학생 연속 검색
- 키보드 중심 입력
- 날짜 기본값 오늘
- 벌점 항목 반복 입력 최소화
- 저장 후 바로 다음 학생
- 같은 종이 시트의 여러 학생을 짧은 시간에 처리

### P2

**벌점 시트 사진 업로드 보조**

```text
사진
 ↓
텍스트/표 인식
 ↓
후보 기록 생성
 ↓
사람이 반드시 검토
 ↓
확정 저장
```

사진 인식 결과를 검토 없이 자동 확정하지 않는다.

## 12. 매일 반별 공지 / 출력

아침 공지를 위해 **오늘의 벌점·반성문 대상 명단**을 학년/반별로 묶는다.

화면:

```text
오늘 공지
├─ G7
├─ G8
├─ G9-A
├─ G9-B
├─ G10
├─ G11
└─ G12
```

필요 기능:

- 날짜 선택
- 학년/반 필터
- 벌점 사유
- 반성문 제출 여부/마감
- A4 인쇄 최적화
- 불필요한 앱 메뉴는 print 시 숨김

이 화면은 “데이터 조회”보다 **통지물을 바로 만드는 기능**으로 설계한다.

## 13. 주간 정산 / 출력


공용 `seondo` / `sasaeng` 계정은 초기 운영용 legacy 계정으로 보고 개인 계정 전환 후 단계적으로 사용을 줄인다.

## 16. Study Planner 연결 — 지금은 연결하지 않음

장기 목표:

```text
학생 포털 / Study Planner
├─ 학습 진척도
└─ 생활점수 현황
```

하지만 지금 두 프로젝트 DB를 직접 결합하면 구조가 굳어질 위험이 있다.

현재 할 일:

1. 학교 공통 `student_no` 확립
2. 두 프로젝트에서 같은 학생을 같은 `student_no`로 식별
3. PIN은 Auth 계층에서 관리
4. 장기적으로 DICS Core Student Directory/Auth 설계

실제 cross-project 데이터 연결은 별도 단계에서 진행한다.

## 18. 데이터 보호 원칙

- 실제 학생 명단/학번/PIN은 Git에 올리지 않는다.
- 학생 이름 목록이 들어간 SQL migration도 Git에 올리지 않는다.
- discipline 앱에는 기능상 필요 없는 생년월일/성별을 복제하지 않는다.
- 출력물은 업무상 필요한 최소 정보만 포함한다.
- 사진 업로드 기능이 도입되면 보존 기간과 삭제 정책을 함께 정의한다.
